## Summary

为萨摩耶「小六二」建立一套可持续复用的 AI 视频短剧生产线：以真实照片为外形参考，用 MiniMax H3 生成竖屏（9:16）搞笑短剧。

**2026-10-23 重做后的设定**：小六二 1 岁半 = 人类 20 岁 = **大学生**，**专业相声**。画面里始终是萨摩耶狗（建模不变），但**它会说人话**——这是主线核心，由它第一人称自述。笑点来自「相声专业要求 vs 狗的身体限制」的错位，而不是狗做复杂的人类动作。单集 **3 分钟左右**。

方案的核心判断是：**这个项目的成败不取决于剧本创意，而取决于跨镜头的小六二形象一致性**。因此全流程围绕「角色资产库 + 单镜头验证 + 768P 试错 / 2K 定稿」三件事设计，而不是围绕「一次生成一整集」。

H3 的硬约束（15 秒单次上限、9 图参考上限、单次只能一个镜头）决定了：**必须按镜头逐条生成再剪辑**，不存在「一次生成一集」的路径。真实素材主要作为参考图/参考视频喂给 H3；**幼犬真实视频可作闪回直接入片**（统一调色 + 颗粒 + 24fps 后与生成素材混剪）。

项目落在 `~/Movies/Xiaoliuer/`，采用「原片只读 / 三层分离 / 文件名自我表意」的素材管理规范，文本类文档纳入 Git 版本控制，媒体文件不进 Git。详见第十二节。

在 MCode 侧建立 5 个专用 Agent（小六二制片人 / 剧情策划·编导 / 编剧·分镜师 / 视觉提示词工程师 / 素材管理员·质检），全部以项目目录为默认工作区，写入范围互不重叠。由于 MCode 的会话工作区创建即锁定、不可迁移，当前对话不搬移而是**把上下文固化为文件**（`docs/项目手册.md`），让新 Agent 下的会话从文件重建上下文——这比搬运对话记录更可靠。详见第十三节。

## 二、H3 能力边界（已核实，以此为方案地基）

来源：MiniMax 官方模型卡 + 官方提示词指南 + 本地 skill 规范 `write-h3-prompts`，并与公开文档交叉验证。

**输出规格**
- 时长：4–15 秒，**整数秒**，不能是 3.5 秒
- 分辨率：768P 或 2K（社区流传的 1440p 不是官方档位）
- 帧率 24 FPS，音频 32 kHz 立体声，音画同生成
- 画幅：21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16（文生视频和参考生成需指定；首尾帧模式跟随输入图比例）
- 对白语言：稳定支持 11 种，含中文
- 提示词上限 7000 字符
- 请求体上限 64 MB

**三种生成模式**

| 模式 | 输入 | 本项目用途 |
|---|---|---|
| T2VA 文生视频 | 仅文字 | 备用（空镜、无角色镜头） |
| FL2VA 首/尾帧 | 0–2 张图 | 跨镜头衔接：把上一镜尾帧当下一镜首帧 |
| **Ref2VA 多模态参考** | ≤9 图 + ≤3 视频(总≤15s) + ≤3 音频(总≤15s)，混合合计 ≤12 个文件 | **主力模式**，角色与场景一致性靠它 |

**关键限制（引用官方文档原文要点）**
- 参考图片：JPG/JPEG/PNG/WEBP/HEIC/HEIF，单个 ≤30 MB，宽高各 256–5760 px
- 参考视频：MP4/MOV，H.264/H.265，音频 AAC/MP3，单个 ≤50 MB，单段 2–15 秒，**总时长 ≤15 秒**
- 音频不能单独作为参考，必须至少配一张图或一段视频
- 首尾帧模式与参考素材模式**互斥**，不能混用
- 单次任务 = 一个镜头。生成耗时通常 15–30 分钟

**计费**
- 覆盖该模型的 M Plan 套餐走周额度；否则扣账户积分。旧版 Token Plan 额度不能支付 H3
- 768P 调提示词、2K 出定稿，是官方与实践共同推荐省钱路径
- 计费以官方平台实际报价为准，本方案不写死单价

**H3 Max 与 H2.3**
- H3 Max：约 20 秒出片，但**只支持首/尾帧，不支持多模态参考**——本项目必须用 **H3.0 (`MiniMax-H3`)**，因为角色一致性完全依赖参考素材模式
- H2.3：更便宜但**输出无声**，本项目有台词和音效，不适用

## 三、核心风险与设计对策

这是方案里最需要被认真对待的部分。AI 视频短剧失败，90% 不是败在创意，而是败在一致性。

### 风险 1：角色跨镜头「换脸」（最高风险）

**成因**：H3 每次生成都是独立的推理过程，不记得上一镜。喂进去的参考图如果不够「权威」，每个镜头的小六二会长得不一样。

**对策**——这是本方案最重要的设计：

1. **每个角色只有一张权威定妆照（Character Sheet）**，不是一堆随手拍。多张不同角度/光线/表情的照片喂进去，模型会在它们之间摇摆，产出谁都不像的「平均脸」。
2. **参考图严格控制在 3–4 张**：定妆照 + 场景图，必要时加一张同镜头的动作参考视频。官方明确指出一张干净的参考胜过五张互相矛盾的参考。
3. **提示词里锁定 retention 等级**：主角标 `fully_preserved`。
4. **先验一个镜头再批量**：花钱之前先用 1 个镜头确认小六二长得像，后面才有意义。

### 风险 2：真实人物（佳佳/恒姐/冰哥）的肖像一致性

真人一致性比狗更难，而且涉及肖像使用。同时孩子在成长记录里出现也有隐私考量。

**对策**——建议的设计，而不是限制：
- **人类角色默认「弱出镜」**：以声音、画外音、手部特写、背影、进门动作为主。观众听得出是姐姐/妈妈/爸爸就够了，不需要看清脸。
- 需要正脸时，用真实照片做参考 + `fully_preserved`，并作为单独镜头处理。
- 这样既保留「这是我家」的真实性，又绕开技术最难的部分。

### 风险 3：狗做人类动作时肢体畸变

「狗握手」「狗点头比划」这类拟人动作最容易崩。**但本系列的主线是「狗说人话」**，
所以风险点转移到了另一处：**犬类口腔结构与人类差异极大**（无法卷舌、犬齿、口腔开合幅度），
H3 生成「狗说中文」很可能得到含混的咕噜声或犬吠，而不是可辨识的普通话。

**对策**（现行方案详见 `bible/series.md` §8）：

1. **先做 3 个镜头的技术验证**（正面说话 / 侧脸说话 / 叼东西说话各一个），
   这 3 个镜决定全季的台词策略，必须在批量生成**之前**做。
2. **镜头设计向低口型难度倾斜**：侧脸、背对、低头、嘴部被毛或物体遮挡（叼笔、埋头、舔鼻子）。
   台词照样有，但观众不看嘴也能接受。
3. **台词声音走后期配音**，H3 只负责画面 + 环境音。这样台词准确率、语速、咬字全部可控，
   口型只是锦上添花，不是承重墙。
4. 狗的身体语言仍然是真实的（歪头、甩尾、耳朵后压、趴下、踱步），
   台词内容可以完全是成年人的——**这个错位本身就是笑点，不要在提示词里把它抹平**。

### 风险 4：15 秒塞太多内容导致失控

**对策**：单镜头控制在 **4–6 秒**，一个镜头只承载**一个动作 + 一个镜头运动**。超过 6 秒或塞两个动作，就拆成两镜。

### 风险 5：3 个月大的素材可能已经找不到了

成长线起点需要幼犬期素材。如果照片已丢失，试播集时间锚点可下调到「到家第一周」。

### 风险 6：磁盘空间紧张

当前数据盘 **460 GB 中已用 367 GB，仅剩 55 GB（87%）**。

AI 视频管线的空间开销：手机原始视频很重（尤其 4K/ProRes），单文件可达数 GB；每次 2K 生成约几十 MB，一集 30–40 次生成约 1–2 GB；参考素材还需转码副本。

**对策**：原片只入一次库，之后立刻转码出小体积参考副本；每集定稿后清理废弃生成结果，只保留入选镜头。见 12.6 的空间管理策略。

## 四、全流程总览

```
阶段 0  素材入库与体检        → 建立素材库，跑 H3 媒体预检
阶段 1  角色圣经 + 场景圣经   → 定妆照定版、性格档案、成长时间线
阶段 2  试播集剧本            → 起承转合 + 笑点设计
阶段 3  分镜表                → 逐镜头拆解：景别、运镜、时长、参考素材
阶段 4  单镜头验证 ⭐          → 先花小钱验 1 个镜头，确认形象对
阶段 5  批量生成 + QC 挑选    → 768P 试错 → 2K 定稿，每镜 2–3 个变体
阶段 6  剪辑 + 字幕 + 发布     → 剪映/CapCut，竖屏 9:16
```

阶段 4 是整个流程的风险闸门。跳过它直接批量生成，是这个项目最容易犯的错。

## 五、职责分工：你做什么 / AI 做什么

你是零基础导演，所以这份分工是刻意设计的：**你只做 AI 做不了的事——提供真实素材和做审美判断。**

| 环节 | 你做 | AI（Agent 团队）做 |
|---|---|---|
| 素材 | 提供照片/视频，挑选哪张最像 | 体检、压缩、裁剪、转码到 H3 规范；建索引 |
| 角色设定 | 确认「小六二就是这个样子」 | 写性格档案、动作习惯库、成长时间线 |
| 剧本 | 说「这集想讲什么」+ 审核好不好笑 | 写剧本、设计笑点结构、起承转合 |
| 分镜 | 说「节奏太慢/太快」 | 逐镜头拆解景别、运镜、时长、场景调度 |
| 提示词 | 不需要参与 | 按 H3 官方六段式格式写、review、压缩到 7000 字符内 |
| 生成 | 确认要花钱 | 提交、轮询、下载、归档、按 2K 优先级重生成 |
| 质检 | 凭直觉看「像不像、好不好笑」 | 逐项核对形象一致性/口型/动作完成度/可剪辑性 |
| 剪辑 | 定最终版 | 可出剪辑清单（时间轴、字幕文案、卡点） |

你的核心工作只有三件：**给素材、做判断、说人话**。其余全部由 Agent 团队承担。

## 七、阶段详解

### 阶段 0：素材入库与体检

**你需要提供：**

| 类别 | 数量建议 | 规格要求 |
|---|---|---|
| 小六二·成年定妆照 | **3–5 张 → AI 挑出 1 张定版** | 正面或 3/4 侧，五官清晰，不戴帽子/墨镜，不遮挡，纯色或干净背景，自然光 |
| 小六二·幼犬期（3 个月左右） | 同上，3–5 张 | 同规格；若找不到可放宽 |
| 狗朋友 | 每只 3–5 张 | 同上 |
| 佳佳 / 恒姐 / 冰哥 | 每人一组近照 | 若采用弱出镜策略，1–2 张足够 |
| 小六二日常视频 | 每段 2–15 秒 | 剪出小六二的招牌习惯动作（如某个歪头、某个扑人方式） |
| 家里客厅 / 小公园 | 各 2–3 张 | 你自己拍的实景照，AI 需要学这个空间长什么样 |

**为什么定妆照这么重要**：H3 生成的一切画面质量上限，由你喂进去的那张图决定。这是你在整个项目里**影响力最大的一个动作**。

**AI 会做的**：逐个文件检查格式/分辨率/时长/大小是否符合 H3 规范 → 不合规的生成调整副本（**不覆盖原文件**）→ 按第十二节命名规范重命名工作副本 → 建 `asset_index.csv` 索引表（文件名 ↔ 角色/场景/习惯动作 ↔ 对应的提示词标签）。

**原片处理原则**：你手机里的原始照片视频**原封不动**保留在 `00_原片/`。AI 体检和处理只作用于 `10_工作素材/` 里的副本。参见第十二节铁律一。

### 阶段 1：角色圣经 + 场景圣经

**角色圣经（每个角色一份）**
- 外形定版：基于定妆照的**逐字特征描述**（毛色分布、脸型、鼻子、耳朵、眼神、身材）
- 性格档案：来自你提供的日常视频——它怎么表达高兴、怎么表达不满、有没有招牌动作
- 成长时间线：3 个月 → 现在，每个阶段的身高/毛量/行为差异（幼犬炸毛 vs 成犬蓬松，这是重要的视觉区分）
- 语言设定：主线狗不说话；它「表达」的方式（表情、动作、叫声节奏）

**场景圣经**
- 家（客厅）的空间布局：沙发位置、地板、光源方向
- 小公园的视觉特征：草地、树、台阶、围栏
- 这两份决定了「每个镜头里的家是同一个家」

### 阶段 2–3：剧本与分镜（示例见第八、九节）

### 阶段 4：单镜头验证 ⭐

**这是最重要的一步。**

流程：拿分镜表里最有代表性的一个镜头（建议是能同时看到小六二全身 + 一个家庭成员 + 客厅空间的镜头），**只生成这一个**。

参数建议：768P、6 秒、9:16、Ref2VA 模式、喂 3 张参考图。

验收四项（缺一不可）：
1. **像不像小六二**——这是唯一的生死线
2. 动作是否完成（不是做到一半就结束）
3. 声音是否自然、台词是否说对
4. 尾帧能否接下一个镜头

只有这四项过了，才进入阶段 5。如果不像，回到阶段 1 换定妆照，而不是在提示词里打补丁——**根因几乎总在参考图，不在提示词**。

### 阶段 5：批量生成

**两级生成策略**（省钱核心）：

```
第一轮  768P + 目标提示词 → 每个镜头生成 2–3 个变体 → 人工挑最好的构图
第二轮  用选中的构图定稿 → 同一提示词出 2K → 必要时微调提示词只改一个变量
```

关键纪律：**一次只改一个变量**。形象不对改参考图，动作不对改动作描述，运镜不对改运镜词。同时改三处，你就无法归因，下次也不知道该怎么改。

**返工预期**：AI 视频一稿过率低。形象漂移和动作做不完是常态，不是意外。预算里必须留出 2–3 倍余量。

**跨镜头衔接**：若镜头 i 和镜头 i+1 需要视觉连续（同一空间、连续动作），用 **FL2VA 模式**：镜头 i 的尾帧作为镜头 i+1 的首帧。代价是失去参考素材模式，所以只在真正需要的衔接处用。

### 阶段 6：剪辑与发布

- 竖屏 9:16，剪辑用剪映 / CapCut（免费，零基础友好）
- **字幕必须后期加，不能让 H3 生成**——模型生成的中文字幕准确率不可靠。字幕文案由 Agent 提供
- 配音/音效：H3 已生成原生音轨。若需要强化音效或加BGM，在剪映里叠
- 结尾留钩子引导关注下一集

## 十、提示词模板与示例

### Ref2VA 官方格式（六段式，全部英文，台词除外）

```
subject_definitions:
<Subject 1>: [外观逐字描述] from <Picture 1>.
<Subject 2>: [外观逐字描述] from <Picture 3>.
<Subject 3>: [场景描述] from <Picture 2>.

summary:
[reference generation] [一句话说明这个镜头讲什么]

retention_analysis:
<Subject 1> (appears in [Shot 1]): fully_preserved - [保留什么]
<Subject 2>: fully_preserved - [保留什么]
<Picture 2>: fully_preserved - [场景布局与光线]

detailed_description:
The target video is in realistic photographic style.
[Shot 1] [景别]，[运镜]。[场景与光线]。[主体动作，含起止]。[表情细节]。
<Subject 1> (S1) speaks: <d>[Chinese] 台词原文。</d>

overall_soundscape:
[1–4 句英文：环境声 + 动作声 + 非语言人声]

non_diegetic_music:
[1–3 句英文：仅观众听得到的配乐]
```

### 关键写作规则（会写进 agent 的约束里）

1. **每个参考素材只给一个明确职责**——形象归形象、场景归场景、动作归动作、运镜归运镜。绝不要求一张图管所有
2. **`[Shot 1]` 后紧跟景别和运镜**，不要先写全局概述
3. **一个镜头一个主动作、一个主运镜**，辅助运动只服务于同一拍
4. **对白格式严格**：`<Subject N> (S1) speaks: <d>[Chinese] 台词。</d>`，说话人 ID 和 `(S1)` 放在 `<d>` 外面
5. **不写时长和画幅**（时长靠剪辑点控制，画幅靠构图表达）
6. **可见文字用英文双引号**，台词和字幕保持中文原文，不翻译不意译
7. `overall_soundscape` 只写环境声和物理动作声，**不重复台词**；`non_diegetic_music` 只写观众听得到的配乐
8. 单镜 `detailed_description` 控制在 350–500 英文词

### 示例：镜 01（小六二从纸箱探头，6 秒）

```
subject_definitions:
```

**方案：把项目根目录建成 iCloud Drive 的同步文件夹**

```

```

开启路径（二选一）：
- 系统设置 → Apple 账户 → iCloud → 云盘 → 同步文件夹 → 选择 `~/Movies/Xiaoliuer`
- 访达 → iCloud 云盘 → 右键任意文件夹 → 同步此文件夹

**开启时的注意**：macOS 会弹出「是否更新使用该文件夹的应用」——选更新，让剪映/iMovie 指向新位置，否则会继续写旧路径。

**分层存储策略**（iCloud 空间充裕，但本地只剩 55 GB，所以要靠「保持副本」策略控制本地占用）

| 目录 | iCloud | 本地策略 | 理由 |
|---|---|---|---|
| `00_原片/` | 同步 | **保持副本** | 不可再生，每集处理完即备份，建议另存一份到移动硬盘后改为释放本地 |

**这个路径需要你确认。** 在你确认前，我不会创建任何目录或复制任何文件。

### 12.2 专业视频工作的三条铁律

你问「一般视频工作者怎么管理自己的拍摄素材」。核心是三条，AI 流程对这三条的要求比传统剪辑**更严格**：

**铁律一：原片只读，永不修改**

原片是你唯一无法复制的东西——AI 生成的视频花了钱和半小时还能再生，你家小六二三個月大的照片丢了就没了。

H3 的媒体预检可能需要压缩、裁剪、转码来符合规范（30 MB 上限、宽高 256–5760 px 等）。**这些调整永远作用在副本上，原文件一个字节都不动。** 这也是 `write-h3-prompts` 规范的硬性要求。

**铁律二：三层分离**

```
00_原片/      原封不动的原始素材。只增不改，永不删除
10_工作素材/  处理过的中间产物（给 H3 的参考图、转码视频、缓存）
20_生成结果/  H3 输出，按集数和镜头号组织
30_成片/      最终导出的可发布文件
90_废弃/      废片，随时可清
```

分开的意义：删废片时不会误伤原片；清理工作副本不影响成片；出了问题能追溯到具体是哪一版参考素材生成的。

**铁律三：文件名必须能独立表意**

这是你现在最大的短板。`253_1734673898.mp4` 这样的名字在日常回看还能忍，在 AI 流程里是灾难——提示词写「使用 `<Picture 1>`」，你无法知道 Picture 1 是哪张狗。**AI 流程的每一份素材都必须有一个能自我解释的 ID。**

命名规范：

| 类型 | 格式 | 示例 |
|---|---|---|
| 小六二·幼犬 | `x6_puppy_<角度>_<序号>` | `x6_puppy_face_01.jpg` |
| 小六二·成年 | `x6_adult_<姿态>_<序号>` | `x6_adult_sit_02.jpg` |
| 狗朋友 | `dog<名字拼音首字母>_<姿态>_<序号>` | `dogdoudou_sit_01.jpg` |
| 家庭成员 | `person_<称呼>_<角度>_<序号>` | `person_jiajia_face_01.jpg` |
| 场景 | `scene_<地点>_<序号>` | `scene_livingroom_01.jpg` |
| 习惯动作 | `habit_<动作>` | `habit_headtilt.mp4` |
| 生成结果 | `ep01_sh<镜号>_v<版本>_<规格>` | `ep01_sh01_v3_2k.mp4` |

文件名和提示词里的标签一一对应，`x6_puppy_face_01.jpg` → `<Picture 1>`，永远能对上。

### 12.3 备份（3-2-1 规则）

AI 素材丢了要花钱重做，原片丢了找不回来。至少满足：3 份副本、2 种介质、1 份在异地。

**iCloud 同步已解决其中两份**：本地 Mac 一份、iCloud 一份。但 iCloud 和本机是同一个账号、同一地点，账号被盗或设备损坏会同时丢失两份——**所以还差一份异地副本**。

建议：`00_原片/` 定期整包拷贝到移动硬盘（或另一个网盘账号）。生成结果（`20_`）不需要异地备份，花钱能重做；`00_原片/` 必须有。

需要绑定账号或接移动硬盘时，我会明确告诉你。

### 12.5 版本控制：文本用 Git，视频不用

一个反直觉但很重要的专业做法：

- **文本类文件**（剧本、分镜、提示词、圣经）→ **纳入 Git 版本控制**。改坏了能回滚，改了什么一目了然，第 2 集写崩了还能翻出第 1 集怎么写的。
- **视频/图片** → **不进 Git**。二进制文件会让仓库迅速膨胀到无法使用。

```bash
cd ~/Movies/Xiaoliuer
git init
cat > .gitignore <<'EOF'
# 媒体文件不进版本控制
00_原片/
10_工作素材/
20_生成结果/
30_成片/
90_废弃/
*.mp4
*.mov
*.jpg
*.png
*.jpeg
*.webp
*.wav
*.mp3
EOF
git add bible/ episodes/ prompts/ docs/ .gitignore
git commit -m "初始化：小六二短剧项目"
```

这样每个提示词改动都有记录，第 10 集还能追溯到第 1 集为什么这么写。

## 十三、项目区搭建（MCode 组织结构）

### 13.1 MCode 的「项目」是什么

实测确认（2026-10-22）：

| 概念 | 实体 | 说明 |
|---|---|---|
| 项目 | **Agent** | Agent 有 `default_workspace_dir`，用该 Agent 开的每个会话都自动以它为工作区 |
| 对话 | Session | 从属于某个 Agent，`session list` 可按 `agent_name` 过滤 |
| 工作区 | 目录 | 会话**创建时锁定**，`session update` 只支持改 `title` 和 `archived`，无法事后更改 |

**关键限制**：当前这条会话（`mvs_61732c5abd8b44b592ffe0d1fc3d524b`）属于 `mavis` Agent，工作区是临时目录，**无法迁移到新 Agent 下**。这是 MCode 的能力边界，不是配置问题。

### 13.2 应对限制的核心设计

**上下文应该活在文件里，不该活在对话历史里。**

对话历史是易失的——会话会被轮转、压缩、归档，临时工作区会被清理。文件系统是持久的。只要 `~/Movies/Xiaoliuer/` 里躺着完整的圣经、分镜、提示词和素材索引，任何一个新会话打开这个目录，都能从文件重建全部上下文，无需依赖历史对话。

所以「迁移项目」的真实做法不是搬运对话，而是**把上下文固化成文件，让工作区本身成为项目载体**。这比搬运对话更可靠——对话记录有长度上限和轮转机制，文件没有。
