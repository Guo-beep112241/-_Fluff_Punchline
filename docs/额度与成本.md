> 2026-10-23 实测。Ep1 批量投产时撞上额度耗尽，这里把机制和操作纪律写死。

**两个池子都空了，H3 和 Hailuo 都提交不了。**

| 模型 | 探针 | 结果 |
|---|---|---|
| MiniMax-H3 | 4 秒（277 credits） | ❌ 402，`the remaining M Plan weekly limit and account credits cannot cover...` |
| MiniMax-Hailuo-2.3 | 6 秒（280 credits） | ❌ 402，`the configured payment sources have insufficient allowance or credits` |

**新发现：两个池子是连着记账的。** H3 的报错里那句
「earlier generations have **280** credits in pending charges」——
280 正是 Hailuo 6 秒任务的价钱。所以 Hailuo 的挂账会占到 H3 的额度上。
（昨天 H3 还能投时，Hailuo 也能投；今天两个一起死了。）

**判定方法**（被拒不产生费用，可以随便试）：
```bash
# H3 探针：4 秒最小任务
cat > /tmp/h3probe.json <<'EOF'
{"model":"MiniMax-H3","prompt":"A single white paper sheet on a plain grey table, static camera.","duration":4,"ratio":"9:16","resolution":"768P"}
EOF
mcode-tools connector call connector__matrix__submit_video_generation --args-file /tmp/h3probe.json
```
输出 `code: 0` = 额度已恢复，立刻续投；`code: 402` = 还不行。
报错里会写明实时单价（`this task costs N credits`），可据此反推当前计价。

**恢复后第一条要做的事**：立刻取回上一批的结果。
结果不取回 → credits 挂账占住池子 → 后面的全被拒。

**当前待投量**：Ep1 剩余 32 镜 ≈ 11,937 credits（33 镜 172 秒 × 69.4）。

## 一、计价

H3 **按秒线性计价，约 69.4 credits/秒**。

| 时长 | credits |
|---|---|
| 4 秒 | 277 |
| 5 秒 | 347 |
| 6 秒 | ≈416 |

估算公式：`credits ≈ 69.4 × 秒数`

**怎么算一笔账**：把分镜表里所有镜头的秒数加起来再乘 69.4。
- Ep1：33 镜 / 172 秒 → **11,937 credits**（768P）
- 全季 188 镜 / 约 980 秒 → **约 68,000 credits**
- 全季按 2.5 个变体 → **约 170,000 credits**

要实时验证当前单价，提交一个 4 秒的最小任务，被拒时错误信息里会写明 `this task costs N credits`，据此反推。

## 二、额度不足时的报错与处置

提交被拒时的典型报错：

```
the remaining M Plan weekly limit and account credits cannot cover this
MiniMax-H3 video generation; this task costs 347 credits, and earlier
generations have 347 credits in pending charges that are taken when their
results are retrieved and must be covered first
```

### 关键机制：取回结果才释放挂账

视频生成成功后，**不取回结果，那笔 credits 就一直挂账占着池子**，后续提交会被拒。

**实测验证**：提交 2 个任务时第 2 个被拒 → 取回第 1 个 → 再提交第 2 个，错误里的「pending charges」那句消失。

### 操作纪律（照做，别改）

> **提交 → 立刻取回 → 再提交下一个。**
> 不要攒着一批不取回。攒着 = 挂账 = 后面的全被拒。

`tools/submit_episode_shots.py` 每提交一个就落盘 task_id，正是为了这个：
中断后已跑在平台上的任务 id 绝不丢，可以直接去取回，不用重新提交（重新提交 = 白花额度）。

### 池子真见底时

连 4 秒的最小任务（277 credits）都提交不了，就是池子空了。两条路：

1. **等 M Plan 周额度重置**（在 platform.minimax.cn →「套餐用量」看重置时间）。
2. **充值**：同一页面「账户钱包」「资源包」入口。注意平台上写着
   「本 API Key 适用于按量付费及语音/视频资源包；使用 M Plan 或 Credits 资源时，请改用『套餐详情』中的订阅 Key」。

## 三、Hailuo 2.3 退路（⚠️ 2026-10-24 起也不可用了）

**原判断**：H3 额度耗尽时 Hailuo 2.3 仍能提交成功——因为它走老 Token Plan 额度池
（错误信息里「legacy Token Plan 不能用于 H3」只针对 H3 / H3 Max）。出片约 45 秒。

**2026-10-24 07:45 实测推翻**：Hailuo 2.3 也报 402
（`the configured payment sources have insufficient allowance or credits`，6 秒 = 280 credits）。
**老 Token Plan 池同样见底了。** 而且 Hailuo 的挂账会占到 H3 的额度上（两个池子连着记账）。

所以目前**没有任何可用的视频模型**。唯一出路是等重置或充值。

如果将来老池子恢复，Hailuo 的限制仍然成立：

| 限制 | 后果 |
|---|---|
| **不支持多模态参考** | 只有纯文生视频 + 首帧图生视频。Ref2VA 工作流整个用不了，参考图/参考视频/六段式提示词全部失效 |
| **文本生视频忽略 `ratio`** | 传 9:16 也输出 1366×768 横屏。只有首帧模式按输入图比例走 → 必须先合成 9:16 首帧 |
| **输出无声** | 后期配音反正是我们定的方案，这点反而不是问题 |
| **时长只有 6 秒 / 10 秒** | 我们 26 个 5 秒镜要重做成 6 秒（分镜表要改） |

### 关键结论：靠 AI 合成首帧走 Hailuo，角色保真**不成立**

实测把真实萨摩耶照 + 场景照喂进 `generate_image` 做首帧合成：

- 第一版：出来是「标准萨摩耶」——楔形长头、蓬松厚毛、耳朵偏大、杏仁眼
- 第二版（加全套品种压制词）：**更糟**——头变尖像狐狸、耳朵更大

**AI 图像模型同样有强烈品种先验，文字压不住。**
所以 Hailuo 退路要保住角色，只能用**真实照片做像素级手工合成**（抠像 + 缩放 + 落影 + 光色匹配），不经过生成模型。
这条路每镜都要人工做，成本高、不可批量。

**判断标准**：Hailuo 只在「H3 完全等不到额度」且「该镜对角色保真要求不高」时用（例如纯空镜、背影、远景）。
主角特写和口型镜不能用它。

## 四、出片速度（重要，排期按这个算）

**H3 实际约 131 秒出一条**（5 秒 768P），Hailuo 约 45 秒。

此前按「15–30 分钟/条」估算的 8–17 小时挂机是**严重高估**。
Ep1 的 33 镜按串行取回算约 **1.2 小时**，不是十几个小时。

### 额度窗口机制（决定性约束）

- **视频模型只受「周窗口」（7 天）限制**，5 小时窗口刷新**不恢复**视频额度。
- 文本、图像、音频、视频**共用同一份额度** —— 跟 MiniMax Code 对话也在扣同一个池子。
- **未用完不累积、不结转**：窗口到期清零，中间断档就白白扔掉。

### 8 集的真实需求（episodes/ep0X/shots.json 实测）

彩蛋用真实素材直用，不生成 → 不占额度。

| 项 | 值 |
|---|---|
| 镜头数 | **207 镜** |
| 总时长 | **974 秒** |
| H3 768P 单版 | **67,596 credits**（974 × 69.4）≈ ¥473 |
| 2 版 | 135,191 credits ≈ ¥946 |
| 3 版 | 202,787 credits ≈ ¥1,420 |

### 结论一：Build 的一个周窗口**装不下** 8 集

不依赖任何估算的论证：

- 你现在的 **Explore（= Build 的 1/4）周额度已经 100% 用光**，
  而这 4 天里只生了 **9 条**视频（4 条 H3 2K 6s + 3 条 H3 768P 5s + 镜01 + 1 条 Hailuo）
  外加一点 Agent 对话。
- 8 集需要 **207 条** = 已生条数的 **23 倍**。
- Build 只给 **4 倍**。→ 23 > 4，**单周必然不够**。

推算（仅供量级参考）：Explore 周窗口 ≈ 1 万 credits → Build ≈ **4 万 credits/周**
≈ 8 集单版的 **56%**（约 4.5 集/周）。要 8 集单版得**跨 2 个周窗口**（每周 4 集），
2 版得跨 4 周，且这两周**基本不能碰 MiniMax Code 对话**（共用池）。

### 结论二：比升级 Build 更省的做法 —— **充值积分包**

- 积分包 **1,000 积分 = ¥7**，与按量目录价等值，**有效期 1 年**（不会过期，不结转问题不存在）。
- 扣费顺序：**先扣套餐内额度 → 再扣积分**。所以**套餐额度用完后，积分会自动接手**，不需要换 Key。
- 8 集单版 ≈ 67,596 credits ≈ **¥473 等值积分**（2 版 ≈ ¥946）。
- 对比：升级 Build 拿到的是**每周重置、过期作废**的额度；积分包是**买了就存着**。
  制作节奏是「每周做 2–3 集」的话，积分包明显更合适。

**操作注意**：走普通 API Key（按量计费）要单独充账户余额；
**积分包要用订阅 Key（sk-cp-…，在「套餐详情」页）**，和 M Plan 额度同一条扣费链。

### 结论三：必须马上处理的一件事

**Explore 自动续费已关闭 + 2026-11-20 到期 + 积分余额 0。**
→ 11-20 之后连 Explore 都没了，视频额度直接归零。三个选项：
① 到期前充值积分包（推荐，1 年有效）；② 重新订阅 Explore（月 ¥59.50，注意官方写明
「关闭后无法重新开启自动续费」）；③ 升级到 Build（额度 4 倍，但按周作废）。

### 怎么自己查到绝对额度数值

官方文档给的三种方式（都只给百分比或相对倍数，绝对值要靠控制台）：

```bash
# 方式一：MiniMax CLI（需先装 mmx）
mmx quota

# 方式二：网页
# https://platform.minimax.cn/console/usage   → 「套餐用量」看百分比与重置时间

# 方式三：API（需要 API Key / 订阅 Key）

  --header 'Content-Type: application/json'
```
